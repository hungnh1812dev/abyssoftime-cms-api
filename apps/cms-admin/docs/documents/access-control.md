# Access Control (Users, Roles, Permissions, Access Tokens, Invites)

`src/pages/admin/settings/{UsersPage,RolesPage,PermissionsPage,AccessTokensPage}.tsx`, `src/hooks/{useUsers,useRoles,usePermissions,useAccessTokens}.ts`, `src/lib/roles.ts` — the four `super_admin`/`admin`-gated settings screens that manage who can do what. All four route at `minRole="admin"` (Users) or `minRole="super_admin"` (the other three) — see [app-shell.md](./app-shell.md)'s router table — and are additionally sidebar-gated by permission slug (see [navigation-shell.md](./navigation-shell.md)).

## `lib/roles.ts` — `roleLevel`

The one piece of role-hierarchy logic client-side: a hardcoded map `{ super_admin: 4, admin: 3, editor: 2, guest: 1 }` (unknown/`null` role → `0`). Used to gate "can I manage this other user" (`UsersPage`), populate the invite/role-change dropdowns with only roles strictly below the caller's own (`rolesBelow`), and by `ProtectedRoute`'s `minRole` check (see [auth.md](./auth.md)). This is a **separate, hardcoded** hierarchy from the `level` field on API-managed `Role` records (`RoleItem.level`, 1–99, edited in `RolesPage`) — the two are not the same system. `ALL_ROLES` in `UsersPage` is likewise a hardcoded 4-slug array, independent of whatever roles actually exist via `useRoleList()`; a role created through `RolesPage` with a 5th slug would not appear in the invite/role-change dropdowns on `UsersPage` at all.

## Users (`UsersPage`, `hooks/useUsers.ts`)

Paginated user list (`GET /api/users`, 20/page) with inline role-change (`PUT /api/users/:id/role`) and delete (`DELETE /api/users/:id`), both restricted client-side to rows where `!isMe && roleLevel(myRole) > roleLevel(user.role)` — a same-or-higher-role peer can't be managed from this UI (server-side enforcement is a separate concern, not documented here). Also renders the invite flow inline on the same page (`useCreateInvite`/`useInviteList`/`useRevokeInvite`, see [locales-and-invites.md](./locales-and-invites.md)) — invite management has no hooks file of its own; it lives in `hooks/useInvites.ts` alongside `useAcceptInvite`.

## Roles (`RolesPage`, `hooks/useRoles.ts`)

Full CRUD over `/api/roles`. `RoleItem.isDefault` roles (the seeded `super_admin`/`admin`/`editor`/`guest`) can't be deleted and have their `name`/`level` fields disabled in the edit dialog (permissions remain editable even for default roles). `RoleDialog`'s `PermissionTree` is a tri-state (checked/indeterminate/unchecked) checkbox tree grouped by permission-slug resource prefix (`resourceOf`: text before the first `:`), with select-all and per-group toggle-all. Create requires `slug` (immutable after creation — the slug input is disabled in edit mode); level range is UI-enforced 1–99 (`<input type="number" min={1} max={99}>`, not further validated).

## Permissions (`PermissionsPage`, `hooks/usePermissions.ts`)

Full CRUD over `/api/permissions` — the permission-slug catalog itself, not role assignments (that's `RolesPage`'s `PermissionTree`). Slug format is enforced client-side via `SLUG_PATTERN = /^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*$/` (`resource:action`) and is immutable after creation. A dedicated info line makes explicit that creating a permission slug here **grants nothing by itself** — a developer must add a matching server-side check before it does anything; this page only manages the catalog and its assignment to roles. Delete failures (e.g. a permission still referenced by a role) surface per-row via `deleteErrors` state rather than a global toast — the only settings page that handles delete-failure display this way (contrast with Users/Roles/Access-Tokens, which just log to the console/rely on the mutation's default toast).

## Access Tokens (`AccessTokensPage`, `hooks/useAccessTokens.ts`)

Full CRUD over `/api/access-tokens`, minus update — tokens are create/list/delete only (no edit). The scope picker is hand-built (not driven by `usePermissions()`'s catalog): a fixed `DOCUMENT_ACTIONS` list (read/create/update/delete/publish/unpublish) plus per-content-type read scopes (`document:read:<slug>`, populated from `useContentTypes()`) that are mutually exclusive with the blanket `document:read` scope (`toggleScope` clears the per-type scopes when `document:read` is checked, and vice versa), plus two fixed "Other" scopes (`media:read`, `content_types:read`). This scope vocabulary is independent of — and does not reuse — the `permissions:*`/`roles:*` catalog from `PermissionsPage`; access-token scopes and user/role permission slugs are two separate authorization systems that happen to share some naming conventions (`resource:action`). The freshly-created token's plaintext value is shown exactly once (`createdToken` state, cleared on dialog close) with a copy-to-clipboard button — the list view only ever shows `token.prefix + "••••••"`.
